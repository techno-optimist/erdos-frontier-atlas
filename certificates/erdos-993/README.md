# Erdős #993 — tree independence-sequence unimodality

**Question** ([erdosproblems.com/993](https://www.erdosproblems.com/993)): is
the independence sequence of every tree unimodal? Writing `i_k(T)` for the
number of independent vertex sets of size `k`, is there always an `m` with
`i_0 ≤ … ≤ i_m ≥ i_{m+1} ≥ …`? Alavi–Malde–Schwenk–Erdős (1987) showed the
answer is **no** for general graphs — every inequality pattern is realised —
which is what makes the tree case interesting.

Replay:

```bash
python3 -I verify.py
```

## What this certificate establishes

Two things, and the first may matter more than the second.

**1. An independent replication of the published frontier.** The state of the
art is Brett Reynolds, *"Mean bounds, structural reductions, and exhaustive
verification for tree independence polynomial unimodality"*, Zenodo v3, DOI
[10.5281/zenodo.19100781](https://doi.org/10.5281/zenodo.19100781), March 2026:
all **8,691,747,673** trees on `n ≤ 29` verified, zero counterexamples. It is a
single-author, non-peer-reviewed preprint with one external citation
(Hibi–Kara–Vien, arXiv:2604.18824), and **nobody had ever replayed it**.

This certificate re-derives that entire range from scratch — different code,
different generator, different machine — and reaches the identical total,
`8,691,747,673`, with zero unimodality violations and per-`n` counts matching
OEIS A000055 exactly at every order.

**2. The next rung.** See `RESULT.json` for the verified range this run
establishes beyond `n ≤ 29`.

## Cost, stated plainly

`n = 30` alone holds **14,830,871,802** trees — **1.71× the entire cumulative
n ≤ 29 workload**. It is not an incremental step past 29; it is more trees than
every published verification of this conjecture combined. Budgeting it as
"one more order" is off by a factor of ~1.7 on total work.

## Generation — WROM, and the three traps

Trees are enumerated by the Wright–Richmond–Odlyzko–McKay constant-amortised-
time algorithm (SIAM J. Comput. **15** (1986) 540–548), the algorithm behind
nauty's `gentreeg`. It generates canonic rooted level sequences and keeps the
*primary* ones — rooted at the **eccentricity centre**, not the centroid.

Three traps, each guarded in `unimodal.c`:

- **centre vs centroid** — both give valid canonical forms with the same count
  but different representatives; mixing them is incoherent;
- **dropping the size tie-break** — bicentral trees whose halves have equal
  height but unequal size get emitted **twice**;
- **reversing the lexicographic tie-break** — still gives the right count while
  duplicating and omitting trees *simultaneously*.

Counts are pinned to OEIS A000055 at every `n` in `--selftest`, so any of these
fails loudly rather than silently changing what "exhaustive" means. This is not
hypothetical: a first attempt at the generator produced A000081 (rooted trees)
instead of A000055, and only the count check caught it.

## The independence polynomial

Exact integer DP over the rooted tree:

```
A_v = ∏_c (A_c + B_c)     (v excluded)
B_v = x · ∏_c A_c         (v included)
I(T,x) = A_root + B_root
```

`Θ(n²)` **coefficient** operations, not linear — the common "runs over a tree
in linear time" claim counts a polynomial multiplication as unit cost. Every
coefficient fits comfortably: the maximum `i_k` over all trees on 30 vertices
is `C(29,14) = 77,558,760`, attained by the star, so `uint64` cannot overflow
here.

## Unimodality, not log-concavity

The test finds the first strict descent and then requires no later strict
ascent. **Plateaus are legal** — a plateau is not a violation.

Testing log-concavity as a proxy would be a serious error: log-concavity is
**false** for trees from `n = 26` onward (Kadrawi–Levit–Yosef–Mizrachi,
arXiv:2305.01784, found exactly two order-26 trees that are unimodal but not
log-concave, and arXiv:2510.18826 found tens of thousands more between 27 and
101 vertices). A log-concavity test would report those as counterexamples to
unimodality. They are not.

Planted failures in `--selftest` pin this down: a genuinely non-unimodal
sequence must be REJECTED, a plateau must be ACCEPTED, and a monotone sequence
must be ACCEPTED.

## A sharding bug worth recording

The per-`n` self-test is unsharded and passed. The cumulative total did not:
it exceeded the published figure by exactly **24**. Cause — the `n ≤ 2` case is
generated by no loop, so each of 13 shards claimed it, inflating `n=1` and
`n=2` by 12 each. Fixed by attributing it to shard 0 only.

The lesson generalises: a per-item check that passes says nothing about a
total that is assembled differently. Checking the sum against an independently
published number is what caught it.

## What this does not do

- It does not prove the conjecture, and no finite sweep can. The realistic
  deliverable was always a verified-to-`n` record.
- It says nothing about log-concavity, which is already known false here.
- The frontier holder is **actively working this problem** (repo pushed
  2026-07-22, cloud compute). A verified-to-`n` record in this lane has a
  short shelf life, and that is fine: the replication half does not.
